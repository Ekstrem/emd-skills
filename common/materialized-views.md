# Materialized Views — проектирование

> Сущности на уровне БД, проецируемые из доменных событий.
> Вход: секция 7 (Created Events) Aggregate Design Canvas.
> Атрибуты колонок коррелируют с Query API Response DTO (артефакт 4).

## Принцип

Materialized View (MV) — денормализованная таблица в Read Store, оптимизированная под конкретный сценарий чтения. Каждая MV обслуживает один или несколько GET-эндпоинтов Query API.

**Проецирование:** ProjectionHandler подписан на EventBus, получает DomainEvent и выполняет INSERT/UPDATE/DELETE в MV.

**Корреляция:** колонка MV → поле Response DTO Query API. Один-к-одному.

## Типы проекций

| Тип | Описание | Пример |
|-----|---------|--------|
| **Основная** | Полное состояние агрегата | {ctx}_sessions |
| **Специализированная** | Подмножество данных | {ctx}_queue |
| **Append-only** | Только INSERT, история | {ctx}_messages |
| **Агрегированная** | Счётчики, суммы | {ctx}_stats |
| **Убывающая** | DELETE при изменении состояния | {ctx}_queue |

## Правила проектирования

1. **Одна MV — один сценарий чтения.** Не обслуживай все запросы из одной таблицы.
2. **Денормализация — нормально.** Дублирование допустимо.
3. **Идемпотентность.** Используй Version как idempotency key: `WHERE version < $event.version`.
4. **Индексы под запросы.** Каждый GET Query API должен иметь поддерживающий индекс.

## Связь событие → проекция

Из секции 7 Aggregate Canvas берутся Created Events:

```
Событие: ChatSessionCreated
  → chat_projections: INSERT (id, user_id, session_id, status='New', actor_login, message_count=1)

Событие: RequestDequeued
  → chat_projections: UPDATE (operator_login, status='InProgress')
```

## Как заполнять через диалог

1. «Какие сценарии чтения нужны? Кто читает и что хочет видеть?»
2. «Какие поля нужны? Из каких событий они берутся?»
3. «Есть ли поля, вычисляемые из нескольких событий?»
4. «По каким полям будет фильтрация и сортировка?» → индексы
